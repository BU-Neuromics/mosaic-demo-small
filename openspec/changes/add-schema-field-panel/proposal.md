# Change: Replace the query page's empty state with the schema itself

## Why

The query view was laid out when the only thing it could produce was a **query**. The
conversational composer was added into that arrangement afterwards, as a fixed 400px
column.

The page has since gained a second, equally common outcome: a **metadata answer** — the
user asks what the data holds, the planner replies by naming fields, and no query is
produced at all. The layout has nowhere to put that:

- the answer lands as prose in the narrow composer column
- the main panel (`minmax(0,1fr)` — most of the screen) renders `.query-blank`, a
  CSS-drawn schematic with a pulse animation reading *"Nothing run yet"*
- the amber lock banner becomes the loudest element on screen, warning about a manual edit
  the user never attempted

So the capability `add-schema-discovery-for-query-building` delivered — the one this whole
line of work exists for — produces the emptiest-looking screen the product has.

**The reframe: there is no "nothing" state.** Before a user has run anything, the most
useful thing to show is *what they can ask about*. The empty state becomes the schema.

## This is NOT the schema-as-data approach we retired

It will look like it. State the difference before anyone has to ask.

`add-schema-as-queryable-metadata` (superseded, archived 2026-09-21) described the schema
**as ingested rows** — one per entity type, one per field — generated from the live schema
and loaded into the store, so that "what fields are on datasets?" became an ordinary query
returning an ordinary table.

| | Retired approach | This change |
| --- | --- | --- |
| **Where the data lives** | Rows **ingested into the store**, regenerated by a script | Live introspection, fetched per session, **never stored** |
| **Can it go stale?** | Yes — it was the only copy of the schema that could drift, which is why it needed a drift check | No. There is nothing to regenerate; it is read from the endpoint that serves the schema |
| **What the user does** | **Runs a query** over `SchemaField` and reads a results table | Reads a panel that is already on screen, next to the conversation |
| **Its role** | It *was* the answer — and it forced a table nobody asked for as a required intermediate step | It is **not** the answer. The conversation still answers; this is the reference beside it |
| **Cost to add a field** | A recipe, a generator, a `make` target, a drift check, and two classes in the deployment's schema | One query Aperture already detects and declines to send |

The retired approach failed because `converse_query_spec` never executes, so the planner
could not read those rows while planning — it could only propose a query over them. That
critique does not apply here: **nothing about this is queried by the planner.** It is
presentation, in the client, of introspection the client already has a right to.

The thing we retired was *storing the schema to display it*. The thing we keep is
*displaying the schema*.

## The data is already advertised, detected, and unused

| Source | Per-slot description? | Status |
| --- | --- | --- |
| `__schema` | **No** — type descriptions only. Verified live: every field is `description: null` | Already queried |
| `hippoSchema` / `hippoEntityType` | **Yes**, plus `kind`, `range`, `role`, `required`, `multivalued`, `identifier`, `targetEntityType`, `enumName`, `enumValues` | Advertised, **detected**, never queried |

`schemaModel.ts:1151` sets `capabilities.schemaIntrospection = 'hippo' | 'graphql'` from a
name-presence check, and **nothing in the app reads it**. `introspection.ts:3-6` states
that richer enrichment waits on *"its query shape confirmed against a live serve"* — that
precondition is now met, verified against the running stack.

This is deferred work the codebase planned for, not new invention.

## What Changes

- **Fetch the enrichment.** One `hippoSchema` query per session, gated on the detection
  that already exists, degrading silently when absent.
- **Carry it on the models.** `ColumnModel` gains `description`, `range`, `kind`,
  `required`, `enumName`. `CollectionModel` gains the entity description `__schema`
  already returns and `deriveCollections` currently discards.
- **A Fields panel replaces `.query-blank`.** The anchor entity's slots, with real
  descriptions, true types and permitted values.
- **Fields are actionable.** `+ filter` appends to the builder **draft**; the column
  toggle is the existing `hiddenFields` state. The standalone field picker is absorbed.
- **The conversation highlights what it named**, presentationally.
- **The lock banner is demoted** from a full-width amber bar to a quiet note inside the
  builder frame.

## Impact

- **Affected specs:** `schema-field-browsing` (ADDED — new capability)
- **Affected code:** all in **`BU-Neuromics/aperture`** (`web/src/data/`, `web/src/query/`).
  Aperture carries no OpenSpec, so the change is tracked here alongside the conversational
  capability it serves; the code lands there.
- **No backend change.** No Mosaic release, no Reel change, no schema change.
- **Depends on** `add-schema-discovery-for-query-building` — this presents what that
  produces.

## Out of scope

- Any change to the shell, nav, visual system, or collections browsing.
- The 1100px breakpoint and the `AppShell` slot contract.
- Server-side field projection (`columns`) — tracked at mosaic#215.
